# SnapTack 仕様書 追補 (v1.8) — 外部連携

本書は SPEC.md (v1.0) / SPEC-v1.x.md (v1.1〜v1.4) / SPEC-v1.5.md (v1.5) / SPEC-v1.6.md (v1.6) /
SPEC-v1.7.md (v1.7) への追補である。既存の仕様は特記なき限り維持する。

対象マイルストーンは `MILESTONES-v1.6.md` の **M22 (外部連携)**。
機能の根拠は `SETUNA2-gap-analysis.md` 4 章を参照。

## 1. 目的と背景

v1.7 までで、スクラップの作成・編集・出力は SETUNA2 相当まで揃った。
ただし**入口はすべて SnapTack の中**にある — ホットキー、トレイメニュー、スクラップリストへの D&D。
「エクスプローラーで画像を選んで SnapTack に渡す」「バッチやランチャーから呼ぶ」といった
**アプリの外からの導線が無い**。

| 課題 | 現状 | 本版での解決 |
|---|---|---|
| 画像ファイルを exe に渡せない | 引数は解釈せず捨てている | コマンドライン引数 (2.2) |
| エクスプローラーから exe へドロップできない | 二重起動で即終了するだけ | 引数経路に相乗り (2.3) |
| 他ツールからキャプチャ・設定を起動できない | ホットキー/トレイのみ | `/C:` オプション (2.4) |
| 決まった範囲を繰り返し切り出せない | 毎回手で選択 | `/R:` オプション (2.5) |

v1.6 (M19) で「exe / トレイアイコンへのドロップ」をスコープ外とした際、
**コマンドライン対応と同じ設計判断になる**ため併せて扱うと決めた (`SPEC-v1.6.md` 3.6)。本版がその受け皿。

### SPEC 4.1 の改訂

`SPEC.md` 4.1 は **「二重起動は禁止 (Mutex)。二重起動時は何も表示せず即終了する」** と定める。
引数付き起動では既存プロセスへ引数を渡す必要があるため、以下のとおり**改訂**する。

> 二重起動は禁止 (Mutex)。二重起動時、**引数があれば既存プロセスへ引き渡してから**即終了する。
> **引数が無ければ従来どおり何も表示せず即終了する。**

**引数なしの挙動は v1.7 以前と完全に同一**である。変わるのは引数付きで起動した場合だけ。

> **不採用**: SETUNA2 は「常駐中に exe を再起動したらキャプチャモードへ入る」挙動を持ち、
> 設定で切り替えられる。SnapTack では採らない — ショートカットの誤ダブルクリックで
> 全画面オーバーレイが出るのは事故として重く、その導線はホットキーと
> トレイメニューで既に足りている。明示的に頼みたい場合は `/C:Capture` (2.4) がある。
> 設定項目を増やさない判断は `SPEC-v1.6.md` 6 の方針とも一貫する。

## 2. 機能仕様

### 2.1 全体像

```
SnapTack.exe [オプション...] [画像ファイルパス...]
                    |
          +---------+---------+
          |                   |
   初回起動 (Mutex 取得成功)   二重起動 (取得失敗)
          |                   |
   常駐を開始してから          名前付きパイプで
   自プロセスで実行            既存プロセスへ送信 → 即終了
          |                   |
          +---------+---------+
                    |
              CommandLineRequest として同じ処理へ
```

**初回起動と二重起動で、引数の解釈結果は同一**にする。受け側を 1 本にすることで
「常駐中かどうかで挙動が違う」という分かりにくさを避ける。

### 2.2 コマンドライン引数

#### 画像ファイルパス

```
SnapTack.exe "C:\pic.jpg" "D:\shot.png"
```

- オプション (`/` 始まり) 以外の引数は**画像ファイルパス**として扱う。
- 読み込みと対応拡張子の判定は既存の `ImageFileLoader` をそのまま使う (`SPEC-v1.6.md` 3.2)。
  webp / avif の扱い、読めないファイルを読み飛ばす方針も同じ。
- 配置は `ScrapManager.AddExternal` 相当 = **カーソル位置を左上**とし、モニタ内へクランプする
  (`SPEC-v1.6.md` 3.4)。複数枚は 1 枚ごとに 24px ずつずらす (`SPEC-v1.6.md` 3.5 と同じ)。
- 生成は必ず `ScrapManager` 経由とする (`SPEC-v1.5.md` 3.1 の中央管理を崩さない)。

> **なぜカーソル位置か**: コマンドラインからの起動でも、ユーザーの注意は
> カーソルのあるモニタにある。他の外部画像経路 (トレイの貼り付け・リストへの D&D) と
> 揃えることで、「外から来た画像はカーソル位置に出る」という一貫した予測が立つ。

#### 引数の扱い

| 入力 | 挙動 |
|---|---|
| 引数なし | 常駐開始 (初回) / 何もせず終了 (二重起動)。**v1.7 と同一** |
| 画像パスのみ | スクラップ化 |
| オプションのみ | 該当動作 (2.4 / 2.5) |
| オプション + 画像パス | 両方実行する。実行順は下記 |
| `/C:Capture` + `/R:` | **`/R:` を優先し `/C:Capture` は無視する** (2.5) |
| 未知のオプション | **無視する。エラーは出さない** |
| 読めないファイル | 読み飛ばす (`SPEC-v1.6.md` 3.2) |

#### 実行順

**`/R:` → 画像パス → `/C:` アクション** の順に処理する。

- **オーバーレイ (`/C:Capture`) は最後**に出す。先に出すと、後続で作った付箋が
  オーバーレイの裏に隠れて「消えた」ように見えるため。
- **`/R:` が先頭**なのは、これが「今の画面」を切り出す操作で、付箋が増える前の画面を
  対象にするのが自然だから。
- `/C:Capture` と画像パスを併用した場合、**先に作った付箋はフリーズ画像に写り込む**。
  実際に画面上に在るものなので、これは意図どおりの挙動である。

**未知のオプションでエラーを出さない**のは、常駐アプリがバッチやランチャーからの誤起動で
モーダルダイアログを出すと、無人実行を止めてしまうため。SnapTack は「一時保持」の道具であり、
引数の検証器ではない。

### 2.3 exe への D&D

エクスプローラーから exe (またはそのショートカット) へ画像ファイルをドロップすると、
**OS がコマンドライン引数として渡す**ため 2.2 の経路にそのまま乗る。追加の実装は要らない。

- 常駐していなければ起動 → 常駐開始 → スクラップ化。
- 常駐中なら二重起動側が引数を送って終了し、**既存プロセスに付箋が増える**。
  二重起動しないので、トレイアイコンは 1 つのまま。

### 2.4 `/C:` オプション

SETUNA2 互換のオプション。**大文字小文字は区別しない**。

| オプション | 動作 |
|---|---|
| `/C:Capture` | キャプチャ (範囲選択オーバーレイ) を開始する |
| `/C:Option` | 設定画面を開く |

- どちらも**既存のトレイメニューと同じ入口へ繋ぐ**。新しい動作は増やさない。
- `/C:Capture` はオーバーレイ表示中なら無視される (`CaptureController` の既存挙動。SPEC 4.3)。
- `/C:Option` は設定画面が既に開いていればアクティブ化する (既存の `OnSettingsRequested` の挙動)。
- 初回起動時の `/C:Capture` は、**常駐の初期化を終えてから**オーバーレイを出す。
  ホットキー登録より先にオーバーレイが出ると、登録失敗の警告がオーバーレイの裏に隠れるため。

### 2.5 `/R:X,Y,W,H` オプション

```
SnapTack.exe /R:100,200,640,480
```

指定した矩形を**範囲選択なしで**キャプチャしてスクラップ化する。

- 座標は**物理ピクセルの仮想スクリーン座標**。SnapTack の座標系規約 (CLAUDE.md) に従う。
  マルチモニタではセカンダリモニタが負の座標を持つため、**X / Y は負値を許す**。
- W / H は正のみ。0 以下や解釈できない値は**オプションごと無視する** (2.2 の方針と同じ)。
- 指定範囲が仮想スクリーン全体からはみ出す場合は、**交差部分にクランプ**する。
  交差が空なら何もしない。
- 生成されたスクラップは**指定した位置にそのまま重なる**。キャプチャと同じ体験
  (「画面から剥がした」。SPEC 4.4) を保つため、カーソル位置は使わない。

> **なぜ画像ファイル経路と配置規則が違うか**: `/R:` は画面上の実在する矩形を切り出すので、
> 元位置が存在する。外部画像 (2.2) は元位置を持たないためカーソル位置に出す
> (`SPEC-v1.6.md` 3.4 と同じ理由)。

#### `/C:Capture` との競合

`/C:Capture` (対話的な範囲選択) と `/R:` (非対話の範囲指定) は**同時に成り立たない**。
両方が指定された場合は **`/R:` を優先し、`/C:Capture` を無視する**。

- **非対話の明示指定を優先する**のは、`/R:` が自動化 (バッチ・ランチャー) のための
  オプションだから。ここで対話を挟むと無人実行が止まる。対話キャプチャはホットキーと
  トレイメニューでいつでも代替できるので、失うものが小さい。
- 引数の**並び順には依存しない**。`/R: /C:Capture` でも `/C:Capture /R:` でも結果は同じ。
- 競合の解決は**引数の解析時**に行う。実行側で捌くと、自プロセス起動とパイプ受信 (2.6) の
  2 経路で判断がズレる余地が残るため。
- `/R:` の値が不正で無視された場合 (2.5) は競合していないので、**`/C:Capture` が活きる**。
- `/C:Option` は別ウィンドウであり `/R:` と競合しない。**両方実行する**。

#### キャプチャ方式

既存の `IScreenCapturer` を使い、**指定矩形を含むモニタをキャプチャしてから切り出す**
(`CroppedBitmap`)。キャプチャのフリーズ方式 (CLAUDE.md) と同じく、実画面を 2 度読まない。

- 矩形が**複数モニタにまたがる場合は、指定位置のあるモニタ内へクランプ**する。
  モニタまたぎキャプチャは混在 DPI の正規化方針が未決のためスコープ外
  (`MILESTONES-v1.6.md` スコープ外表 / `SPEC-v1.x.md` 2.4 の判断を維持)。

### 2.6 IPC: 名前付きパイプ (決定)

| 案 | 判断 |
|---|---|
| **名前付きパイプ (`System.IO.Pipes`)** | **採用** |
| `WM_COPYDATA` | 不採用 |
| メモリマップトファイル | 不採用 |

採用理由:

- **P/Invoke が要らない。** `NamedPipeServerStream` / `NamedPipeClientStream` で完結する。
  SnapTack は P/Invoke を必要な場所に限る方針 (Interop/ に集約) で、増やさずに済む。
- **可変長の引数列を素直に送れる。** 長いパスや複数ファイルでも構造体マーシャリングや
  サイズ上限を気にしなくてよい。`WM_COPYDATA` は受信用の隠しウィンドウと
  ポインタ渡しの構造体が要り、この用途には重い。
- **テストしやすい。** パイプ越しの往復をウィンドウ無しで検証できる。
- 既に `Mutex` で二重起動を判定しているため、**同じ「名前付きカーネルオブジェクト」の
  延長**として理解しやすい (`MILESTONES-v1.6.md` の要判断メモが求めていた性質)。

#### 仕様

- パイプ名: `SnapTack_CommandLinePipe`。Mutex 名と同じく**同一ユーザーセッション内で一意**。
- サーバ (常駐側) は起動時に待ち受けを開始し、終了時に破棄する。
- 送信形式は**引数を 1 行 1 個で並べた UTF-8 テキスト**。JSON にしないのは、
  送るものが「文字列の配列」以上に育つ予定が無く、シリアライザを持ち込む理由が無いため。
- クライアント (二重起動側) は**短いタイムアウト (既定 3 秒) で接続**し、
  失敗しても**エラーを出さず黙って終了する**。常駐側が終了処理中でパイプが閉じている、
  といった競合状態でダイアログを出す価値が無いため。
- 受信した引数は**常駐側の UI スレッドへディスパッチ**してから処理する
  (スクラップ生成もキャプチャも UI スレッド前提のため)。

> **セキュリティ**: パイプは既定の ACL で作り、**同一ユーザーのプロセスからのみ**
> 接続できるようにする。受け取った文字列は画像パスとオプションとしてのみ解釈し、
> **実行や展開はしない**。読めないパスは既存どおり読み飛ばされる。

### 2.7 スコープ外 (M22 では実装しない)

| 項目 | 理由 |
|---|---|
| **トレイアイコンへの D&D** | `NotifyIcon` は標準で D&D を受け付けない。透明な受付ウィンドウをアイコン位置に重ねる等の工夫が要るうえ、アイコン位置は OS のオーバーフロー領域に入ると追跡しづらい。**exe へのドロップ (2.3) で同じ目的を果たせる**ため、実装コストに見合わないと判断した (`MILESTONES-v1.6.md` が「単独で見送り可」としていた項目) |
| 二重起動時のキャプチャ開始 (SETUNA2 相当) | 1 章の改訂メモ参照。誤起動の事故が重く、`/C:Capture` で代替できる |
| 標準出力への結果返却 / 終了コード | GUI アプリ (`WinExe`) はコンソールへ書けない。バッチ連携の需要が確認できてから検討する |
| ファイル関連付け・「送る」メニュー登録 | インストーラーとレジストリに手を入れる。exe への D&D で導線は足りる |
| `/R:` のモニタまたぎ | 混在 DPI の正規化方針が未決 (`SPEC-v1.x.md` 2.4 の判断を維持) |

## 4. 互換性・非機能

- **引数なしの挙動は v1.7 と完全に同一。** 常駐開始も、二重起動時の即終了も変わらない。
- **`settings.json` のスキーマは変更しない。** 本版は設定項目を追加しない
  (二重起動時の動作を設定可能にしない判断の帰結。1 章)。
- **`index.json` の `SchemaVersion` は 2 のまま。** 作られるスクラップは既存の構造で表現できる。
- 操作体系の既存部分は変更しない (`SPEC-v1.x.md` 4)。本版は**画面上の操作を一切増やさない**。
- **起動時間**: パイプサーバの待ち受け開始は非同期で行い、常駐開始をブロックしない
  (「スプラッシュを出さない = 起動速度優先」の設計方針。`MILESTONES-v1.6.md` スコープ外表)。
- `BitmapSource` は従来どおり `Freeze()` する (CLAUDE.md のコーディング規約)。

## 5. 決定事項

着手前に判断が必要だった項目 (`MILESTONES-v1.6.md` M22 の「要判断」) は以下のとおり確定した。

| 項目 | 決定 | 根拠 |
|---|---|---|
| SPEC 4.1 (二重起動) の改訂 | **引数がある時だけ既存プロセスへ渡して終了。引数なしは従来どおり即終了** | 改訂幅が最小で、設定項目も増えない。引数なしの挙動が変わらないので既存ユーザーに影響しない (1 章) |
| 二重起動時のキャプチャ開始を設定可能にするか | **しない (機能自体を採らない)** | 誤ダブルクリックで全画面オーバーレイが出る事故が重い。`/C:Capture` で代替できる (1 章) |
| IPC 方式 | **名前付きパイプ** | P/Invoke 不要、可変長引数を素直に送れる、テストしやすい、Mutex の延長で理解できる (2.6) |
| トレイアイコンへの D&D | **スコープ外** | `NotifyIcon` が D&D を受けず回避策が重い。exe へのドロップで目的を果たせる (2.7) |
| `/R:X,Y,W,H` の要否 | **実装する** | 定型範囲の繰り返し切り出しは自動化の要になる。既存のキャプチャ経路の再利用で済む (2.5) |
| `/R:` の配置位置 | **指定矩形にそのまま重ねる** | 元位置が存在するため。外部画像がカーソル位置なのは元位置を持たないからで、規則は矛盾しない (2.5) |
| 不正な引数の扱い | **無視して継続。エラーダイアログを出さない** | 無人実行を止めないため。常駐アプリが引数の検証器として振る舞う必要は無い (2.2) |
| `/C:Capture` と `/R:` の競合 | **`/R:` を優先し `/C:Capture` を無視する。解決は解析時に行う** | `/R:` は自動化のためのオプションで、対話を挟むと無人実行が止まる。対話キャプチャはホットキーで代替できる。解析時に解決するのは 2 経路 (自プロセス / パイプ) で判断をズラさないため (2.5) |
| オプションと画像パスの実行順 | **`/R:` → 画像パス → `/C:` アクション** | オーバーレイを先に出すと、後続で作った付箋が裏に隠れて消えたように見えるため (2.2) |
